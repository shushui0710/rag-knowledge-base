## 架构设计：JWT认证流程

```
┌──────────┐     ┌──────────┐     ┌──────────┐
│  前端     │     │ 后端      │     │ 数据库    │
│ LoginView│     │ AuthCtrl  │     │  user表   │
└────┬─────┘     └────┬─────┘     └──────────┘
     │ POST /api/auth/login           │
     │ {username, password}           │
     │──────────────────────────────→│
     │                    ┌───────────┤
     │                    │ 1.查询user │
     │                    │ 2.BCrypt验证│
     │                    │ 3.生成JWT  │
     │                    └───────────┤
     │  {user, token: "eyJ..."}       │
     │←───────────────────────────────│
     │                                │
     │  之后每次请求带 Authorization: Bearer eyJ...│
     │──────────────────────────────→│
     │              ┌─────────────────┤
     │              │ JwtInterceptor  │
     │              │ 1.提取token     │
     │              │ 2.解析userId    │
     │              │ 3.存入UserContext│
     │              └─────────────────┤
     │              │ Controller通过   │
     │              │ UserContext.getUserId()│
     │              │ 获取当前用户     │
     │              └─────────────────┤
```

### 认证流程详解

1. **注册**：前端发 username + password → 后端 BCrypt 加密密码 → 存 MySQL
2. **登录**：前端发 username + password → 后端 BCrypt 验证 → 生成 JWT → 返回给前端
3. **前端存储**：JWT 存 localStorage，每次请求放在 `Authorization: Bearer <token>` 头
4. **后端拦截**：JwtInterceptor 拦截所有 `/api/**` 请求（排除 `/api/auth/**`）
5. **用户上下文**：JwtInterceptor 解析出 userId 后，存入 ThreadLocal（UserContext）
6. **业务使用**：Service 层通过 `UserContext.getUserId()` 获取当前用户ID

### 为什么用 JWT 不用 Session？

| 对比项 | Session | JWT |
|--------|---------|-----|
| 存储位置 | 服务端内存 | 客户端（localStorage） |
| 扩展性 | 多服务器需共享session（复杂） | 无状态，天然支持分布式 |
| 安全性 | CSRF风险 | XSS风险（需前端配合） |
| 央国企面试 | 几乎必问 | 理解JWT是基本功 |

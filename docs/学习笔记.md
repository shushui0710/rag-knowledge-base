## 一、技术栈白话版

## 二、RAG 系统整体流程

RAG = Retrieval-Augmented Generation = 检索增强生成

**白话理解**：就像一个智能图书馆——你上传资料，AI 读完后，你提问时它会先去资料库里找相关内容，然后根据找到的内容来回答你，还会标注来源。

### 离线流程（文档入库）

```
用户上传文档
    │
    ▼
┌──────────┐     ┌──────────────┐     ┌──────────┐     ┌────────────┐     ┌──────────┐
│ 文件上传  │ ──→ │ 文档解析      │ ──→ │ 文本分块  │ ──→ │ Embedding  │ ──→ │ Milvus   │
│ 到 MinIO  │     │ PDFBox/POI   │     │ 滑动窗口  │     │ 向量化     │     │ 向量存储  │
│           │     │ 提取纯文本    │     │ 512字/块  │     │ 文本→2048维│     │          │
└──────────┘     └──────────────┘     └──────────┘     └────────────┘     └──────────┘
                                          │
                                          ▼
                                   ┌──────────────┐
                                   │ MySQL        │
                                   │ 存元数据+分块 │
                                   └──────────────┘
```

**每一步在做什么**：
1. **文件上传到 MinIO**：把原始文件存起来（就像把书放到书架上）
2. **文档解析**：用 PDFBox 读 PDF，用 POI 读 Word，提取出纯文本
3. **文本分块**：把长文本切成 512 字一块（就像把一本书拆成一页一页的）
4. **Embedding 向量化**：用智谱 API 把每块文本转成 2048 维的数字向量（机器理解的"语义指纹"）
5. **Milvus 存储**：把向量存到 Milvus 向量库（就像给每块内容建了一个"语义索引"）

### 在线流程（智能问答）

```
用户提问："如何配置数据库连接？"
    │
    ▼
┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│ 问题向量化    │ ──→ │ Milvus 检索   │ ──→ │ Prompt 拼接  │ ──→ │ DeepSeek     │
│ 同样用Embedding│     │ Top-K=5      │     │ 参考资料+问题 │     │ 大模型生成   │
│ 文本→向量     │     │ 找最相关的5块  │     │              │     │              │
└──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘
                                                    │                    │
                                                    │                    ▼
                                                    │             ┌──────────────┐
                                                    │             │ 返回答案      │
                                                    │             │ + 来源引用    │
                                                    │             └──────────────┘
                                                    ▼
                                             ┌──────────────┐
                                             │ MySQL        │
                                             │ 保存对话记录  │
                                             └──────────────┘
```

**每一步在做什么**：
1. **问题向量化**：把用户的问题也转成向量（和文档入库时用同一个 Embedding 模型）
2. **向量检索**：在 Milvus 中找和问题向量最相似的 5 个文本块（Top-K=5）
3. **Prompt 拼接**：把找到的 5 块文本 + 用户问题，拼成一段提示词给大模型
4. **大模型生成**：DeepSeek 根据参考资料生成回答，并标注来源

## 三、第一课：三层架构与核心注解

### 3.1 三层架构

Spring Boot 项目标准的分层结构：

```
前端请求 ──→ Controller ──→ Service ──→ Mapper ──→ MySQL
  HTTP        接收请求      业务逻辑    数据库操作
              返回JSON
```

| 层 | 职责 | 类比 |
|----|------|------|
| **Controller** | 接收 HTTP 请求，参数校验，调用 Service，返回 JSON | 前台服务员 |
| **Service** | 核心业务逻辑，调用 Mapper 操作数据 | 厨师 |
| **Mapper** | 数据库操作（MyBatis-Plus 自动实现 CRUD） | 仓库管理员 |

**为什么要分层？**
- 职责分离：每层只做自己该做的事
- 可维护性：改业务逻辑不会影响数据库操作，反之亦然
- 可测试性：可以单独测试某一层
- 面试重点：这是后端开发的基本功，面试必问

### 3.2 项目中的代码示例

**Controller 层**（`DocumentController.java`）：

```java
@Tag(name = "文档管理")           // Knife4j 接口文档分组名
@RestController                    // 告诉Spring：我是Controller，返回值自动转JSON
@RequestMapping("/api/document")   // 我的根路径是 /api/document
@RequiredArgsConstructor           // Lombok：自动生成构造函数（用于依赖注入）
public class DocumentController {

    private final DocumentService documentService;  // 声明依赖，但不new

    @Operation(summary = "获取文档列表")  // Knife4j 接口说明
    @GetMapping("/list")                  // 处理 GET /api/document/list
    public Result<List<Document>> list() {
        return Result.success(documentService.list());
        // 调用Service拿数据 → 包在Result里 → 返回JSON
    }
}
```

**Service 层**（`DocumentServiceImpl.java`）：

```java
@Service                          // 告诉Spring：我是Service，自动创建并管理我
@Slf4j                            // Lombok：自动生成 log 变量
@RequiredArgsConstructor
public class DocumentServiceImpl implements DocumentService {

    private final DocumentMapper documentMapper;  // 不用new，Spring自动注入

    @Override
    public List<Document> list() {
        // selectList(null) = SELECT * FROM document WHERE deleted = 0
        // null 表示没有查询条件 → 查全部
        // deleted = 0 是 MyBatis-Plus 自动加的逻辑删除条件
        return documentMapper.selectList(null);
    }
}
```

**Mapper 层**（`DocumentMapper.java`）：

```java
@Mapper                           // 告诉MyBatis-Plus：这是一个Mapper接口
public interface DocumentMapper extends BaseMapper<Document> {
    // 空接口！什么都不用写！
    // 继承 BaseMapper<Document> 就自动有了：
    // - selectList(null)     → SELECT * FROM document
    // - selectById(1)        → SELECT * FROM document WHERE id = 1
    // - insert(document)     → INSERT INTO document ...
    // - deleteById(1)        → DELETE FROM document WHERE id = 1
    // - updateById(document) → UPDATE document SET ...
}
```

### 3.3 核心注解详解

| 注解 | 作用 | 白话解释 |
|------|------|----------|
| `@SpringBootApplication` | 标记启动类，开启自动配置 | "我是这个项目的总开关" |
| `@MapperScan("com.liushuwen.rag.**.mapper")` | 自动扫描所有模块的 Mapper | "去所有模块找仓库管理员" |
| `@RestController` | 标记 Controller，返回值自动转 JSON | "我是服务员，说话自动变成JSON" |
| `@RequestMapping` | 设置 URL 路径 | "我在这个门牌号办公" |
| `@GetMapping` / `@PostMapping` | 处理 GET/POST 请求 | "我负责接待这种类型的客人" |
| `@Service` | 标记 Service 层组件 | "我是厨师，Spring自动雇我" |
| `@Mapper` | 标记 MyBatis Mapper 接口 | "我是仓库管理员接口" |
| `@RequiredArgsConstructor` | Lombok 自动生成构造函数 | "帮我写好依赖注入的模板代码" |
| `@Slf4j` | Lombok 自动生成 log 变量 | "给我一个日志记录器" |

### 3.4 依赖注入（DI）

**问题**：为什么 Service 里用 `private final DocumentMapper documentMapper` 而不 `new`？

**回答**：

```java
// ❌ 错误做法：自己 new
private final DocumentMapper documentMapper = new DocumentMapper();
// 问题：DocumentMapper 是接口，不能 new！
// 而且就算能 new，你也控制不了它的生命周期

// ✅ 正确做法：声明依赖，让 Spring 注入
private final DocumentMapper documentMapper;
// Spring 启动时发现 DocumentServiceImpl 需要一个 DocumentMapper
// 就自动找到 DocumentMapper 的实现（MyBatis-Plus动态生成的代理类）
// 通过构造函数注入进来
```

这就是**控制反转（IoC）**——对象的创建权从"你自己 new"反转成"Spring 帮你创建和注入"。

**好处**：
- 解耦：Service 不关心 Mapper 怎么创建的
- 可测试：测试时可以注入 Mock 的 Mapper
- 单例：Spring 默认只创建一个实例，节省内存

### 3.5 MyBatis-Plus BaseMapper 的魔法

继承 `BaseMapper<T>` 后自动获得的 CRUD 方法：

| 方法 | 对应 SQL | 用途 |
|------|----------|------|
| `selectList(null)` | `SELECT * FROM table WHERE deleted=0` | 查全部 |
| `selectList(queryWrapper)` | `SELECT * FROM table WHERE ...` | 条件查询 |
| `selectById(1L)` | `SELECT * FROM table WHERE id=1` | 按ID查 |
| `insert(entity)` | `INSERT INTO table ...` | 插入 |
| `updateById(entity)` | `UPDATE table SET ... WHERE id=?` | 按ID更新 |
| `deleteById(1L)` | `UPDATE table SET deleted=1 WHERE id=1` | 逻辑删除 |

> 注意：`deleteById` 不是真的 `DELETE`，而是 `UPDATE SET deleted=1`。因为实体类配置了逻辑删除，MyBatis-Plus 会自动处理。

### 3.6 请求流转路径（完整）

```
1. 用户点击"文档列表"按钮
2. Vue3 发送 HTTP GET /api/document/list（经 Vite 代理转发到 :18080）
3. Spring Boot 的 DispatcherServlet 接收请求
4. 根据 @RequestMapping("/api/document") + @GetMapping("/list") 找到 DocumentController.list()
5. Controller 调用 documentService.list()
6. Service 调用 documentMapper.selectList(null)
7. MyBatis-Plus 执行 SELECT * FROM document WHERE deleted=0
8. MySQL 返回数据 → MyBatis-Plus 自动映射成 List<Document>
9. Service 返回 List<Document> 给 Controller
10. Controller 用 Result.success() 包装成 {code:200, message:"success", data:[...]}
11. Spring 自动序列化成 JSON 返回给前端
12. Vue3 拿到 JSON，渲染到页面
```

## 四、第二课：项目守护机制

项目骨架里有四个"守护机制"，它们不是业务核心，但保证系统健壮。面试也经常问。

### 4.1 Result 统一响应

**为什么需要**：没有 Result 时，不同接口返回不同格式（有的返回 List，有的返回对象，出错了抛异常），前端无法统一处理。

**Result 就是"标准快递箱"**——不管里面装什么，外面格式统一：

```java
public class Result<T> {       // 泛型<T>：data可以是任何类型
    private int code;           // 200=成功, 400=业务错误, 500=系统错误
    private String message;     // "success" 或具体错误信息
    private T data;             // 实际数据（Document、List<Document>、Void...）
}
```

Controller 里的用法：

```java
public Result<List<Document>> list() {
    return Result.success(documentService.list());
    // 翻译：拿到数据 → 包在Result箱子里 → 贴上200标签 → 发给前端
}
```

前端只需判断 `code === 200` 就知道是否成功，`data` 里拿数据，`message` 里看错误原因。

### 4.2 BusinessException + GlobalExceptionHandler

**BusinessException** = 业务级错误（不是系统崩了，是用户操作有问题）：
- 上传了不支持格式的文件
- 文件太大超了限制
- 文档ID不存在

```java
// 在 Service 里抛出
throw new BusinessException("不支持的文件格式: xyz，仅支持: pdf, docx, md, txt");
```

**GlobalExceptionHandler** = 全局异常处理网，站在所有 Controller 外面：

```java
@RestControllerAdvice  // = @ControllerAdvice + @ResponseBody
// 意思："我是全局Controller助手，返回值自动变成JSON"
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    // 意思："我只接 BusinessException 这种异常"
    public Result<Void> handleBusinessException(BusinessException e) {
        return Result.error(400, e.getMessage());
        // 业务错误 → 返回 400 + 错误信息
    }

    @ExceptionHandler(Exception.class)
    // 意思："其他所有异常我都接"
    public Result<Void> handleException(Exception e) {
        return Result.error(500, "系统内部错误");
        // 系统错误 → 返回 500 + 通用错误信息（不暴露堆栈给前端）
    }
}
```

**效果**：不管哪里抛了异常，前端看到的永远是 `{code, message, data}` 格式，不会看到一堆堆栈信息。

### 4.3 配置类（@Configuration + @Bean）

第三方组件（如 MinIO 客户端）不是 Spring 自带的，Spring 不知道怎么创建。需要用 `@Configuration` + `@Bean` 手动告诉 Spring：

```java
@Configuration                    // "我是配置类，Spring启动时自动读我"
@ConfigurationProperties(prefix = "minio")  // "从yml里读minio开头的配置"
@Data                             // Lombok生成getter/setter
public class MinioConfig {
    private String endpoint;      // 自动映射 yml 中的 minio.endpoint
    private String accessKey;     // 自动映射 yml 中的 minio.access-key
    private String secretKey;     // 自动映射 yml 中的 minio.secret-key
    private String bucketName;    // 自动映射 yml 中的 minio.bucket-name

    @Bean                          // "Spring，按这个方法创建MinioClient对象"
    public MinioClient minioClient() {
        return MinioClient.builder()
                .endpoint(endpoint)
                .credentials(accessKey, secretKey)
                .build();
    }
}
```

**@Bean vs @Service/@Component 的区别**：

| 注解 | 谁创建对象 | 适用场景 |
|------|-----------|----------|
| `@Service` / `@Component` | Spring 自动创建（无参构造） | 自己写的类 |
| `@Bean` | 你写方法手动创建 | 第三方库的类（MinioClient、RestTemplate等） |

### 4.4 @ConfigurationProperties vs @Value

两种从 yml 读配置的方式：

```java
// 方式1：@ConfigurationProperties —— 批量映射
@ConfigurationProperties(prefix = "minio")
// yml: minio.endpoint, minio.access-key, minio.secret-key, minio.bucket-name
// 全部自动映射到对应字段，access-key → accessKey（kebab-case → camelCase）

// 方式2：@Value —— 单值注入
@Value("${rag.chunk-size}")
private int chunkSize;  // 只注入一个值
```

| 方式 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| `@ConfigurationProperties` | 批量映射、类型安全、可校验 | 需要写配置类 | 配置项多（如MinIO的4个配置） |
| `@Value` | 简单直接、一行搞定 | 只能注入一个值、无校验 | 只需要一两个值 |

### 4.6 MyMetaObjectHandler 自动填充

Document 实体里有 `createTime` 和 `updateTime`，标注了自动填充：

```java
// Document.java
@TableField(fill = FieldFill.INSERT)        // 插入时自动填
private LocalDateTime createTime;

@TableField(fill = FieldFill.INSERT_UPDATE) // 插入和更新时都自动填
private LocalDateTime updateTime;
```

但还需要配置一个 Handler 才能生效：

```java
@Component
public class MyMetaObjectHandler implements MetaObjectHandler {
    @Override
    public void insertFill(MetaObject metaObject) {
        // 插入时自动设置 createTime 和 updateTime
        this.strictInsertFill(metaObject, "createTime", LocalDateTime.class, LocalDateTime.now());
        this.strictInsertFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
    }

    @Override
    public void updateFill(MetaObject metaObject) {
        // 更新时自动设置 updateTime
        this.strictUpdateFill(metaObject, "updateTime", LocalDateTime.class, LocalDateTime.now());
    }
}
```

效果：调用 `documentMapper.insert(document)` 时，不用手动 setCreateTime，MyBatis-Plus 自动帮你填上当前时间。

### 4.7 CorsConfig 跨域配置

前端在 `localhost:5173`，后端在 `localhost:18080`，端口不同就是"跨域"。浏览器默认拦截跨域请求。

```java
@Configuration
public class CorsConfig {
    @Bean
    public WebMvcConfigurer corsConfigurer() {
        return new WebMvcConfigurer() {
            @Override
            public void addCorsMappings(CorsRegistry registry) {
                registry.addMapping("/api/**")     // 对所有/api开头的请求
                        .allowedOrigins("*")        // 允许所有来源
                        .allowedMethods("*");       // 允许所有HTTP方法
            }
        };
    }
}
```

| 守卫 | 作用 | 类比 |

| Result | 统一返回格式 | 标准快递箱 |
| BusinessException | 业务级错误 | "这个操作不允许"告示 |

| @Configuration类 | 基础设施配置 | 图书馆的规章制度 |

## 五、第2周实操：文档上传全流程

### 5.1 上传流程总览

文档上传的完整流程分 6 步：

```
用户选择文件
    │
    ▼
Step1: 文件校验（空文件？太大？格式支持？）

@Slf4j
public class MinioService {

                .build()

    private void ensureBucketExists() {
        try {
            boolean exists = minioClient.bucketExists(
                BucketExistsArgs.builder()
                    .bucket(minioConfig.getBucketName())
                    .build()
            );
            if (!exists) {
                minioClient.makeBucket(
                    MakeBucketArgs.builder()
                        .bucket(minioConfig.getBucketName())
                        .build()
                );
                log.info("创建MinIO桶: {}", minioConfig.getBucketName());
            }
        } catch (Exception e) {
            throw new BusinessException("MinIO桶检查失败: " + e.getMessage());
        }
    }

    public String generateObjectName(String fileName) {
        String datePath = LocalDate.now().format(DateTimeFormatter.ofPattern("yyyyMMdd"));

### 5.4 文档解析（DocumentParserService）

不同格式用不同工具解析：

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class DocumentParserService {

    public String parse(MultipartFile file, String fileType) {
        return switch (fileType) {
            case "txt", "md" -> parseText(file);      // 直接读文本
            case "pdf" -> parsePdf(file);              // 用 PDFBox
            case "docx" -> parseDocx(file);            // 用 POI
            default -> throw new BusinessException("不支持的文件格式: " + fileType);
        };
    }

    private String parseText(MultipartFile file) {
        // TXT/MD：直接读取文件内容为字符串
        try {
            return new String(file.getBytes(), StandardCharsets.UTF_8);
        } catch (IOException e) {
            throw new BusinessException("文本文件解析失败: " + e.getMessage());
        }
    }

    private String parsePdf(MultipartFile file) {
        // PDF：用 PDFBox 的 Loader.loadPDF 加载，再用 PDFTextStripper 提取文本
        try {
            PDDocument document = Loader.loadPDF(file.getBytes());
            PDFTextStripper stripper = new PDFTextStripper();
            String text = stripper.getText(document);
            document.close();
            return text.trim();
        } catch (IOException e) {
            throw new BusinessException("PDF解析失败: " + e.getMessage());
        }
    }

    private String parseDocx(MultipartFile file) {
        // Word：用 POI 的 XWPFDocument 加载，遍历段落提取文本
        try {
            XWPFDocument document = new XWPFDocument(file.getInputStream());
            XWPFWordExtractor extractor = new XWPFWordExtractor(document);
            String text = extractor.getText();
            extractor.close();
            return text.trim();
        } catch (IOException e) {
            throw new BusinessException("DOCX解析失败: " + e.getMessage());
        }
    }
}
```

| 格式 | 解析工具 | 核心API | 流程 |
|------|----------|---------|------|
| TXT/MD | 无（直接读） | `new String(bytes, UTF_8)` | 文件字节 → 字符串 |
| PDF | Apache PDFBox | `Loader.loadPDF()` → `PDFTextStripper.getText()` | 二进制PDF → 文本 |
| DOCX | Apache POI | `XWPFDocument` → `XWPFWordExtractor.getText()` | Word文档 → 文本 |

### 5.5 文本分块（DocumentChunkService）

**为什么要分块？**
- 大模型有 token 限制，不能一次输入整篇文档
- 向量检索需要小块文本，太大检索不精准，太小丢失上下文
- 512 字/块是业界常用的平衡点

**滑动窗口分块算法**：

```
原文：[████████████████████████████████████████████████████] 4567字

分块结果：
  Chunk 0: [████████████████████] 512字
  Chunk 1:       [████████████████████] 512字  ← 前64字和上一块重叠
  Chunk 2:             [████████████████████] 512字
  Chunk 3:                   [████████████████████] 512字
  Chunk 4:                         [██████] 118字  ← 最后一块
```

**为什么要有重叠（overlap=64）？**
- 防止在分块边界处切断重要信息
- 比如"数据库连接池的最大连接数是100"，如果正好在"连接池"和"最大"之间切断，两个块都不完整
- 64字重叠确保边界处的信息在两个块中都有

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class DocumentChunkService {

    private final DocumentChunkMapper documentChunkMapper;

    @Value("${rag.chunk-size}")
    private int chunkSize;      // 512

    @Value("${rag.chunk-overlap}")
    private int chunkOverlap;   // 64

    public int chunkAndSave(String text, Long documentId) {
        List<DocumentChunk> chunks = new ArrayList<>();
        int index = 0;
        int start = 0;

        while (start < text.length()) {
            int end = Math.min(start + chunkSize, text.length());
            String chunkContent = text.substring(start, end);

            DocumentChunk chunk = new DocumentChunk();
            chunk.setDocumentId(documentId);
            chunk.setChunkIndex(index);
            chunk.setContent(chunkContent);
            chunk.setCharCount(chunkContent.length());
            chunks.add(chunk);

            index++;
            start += chunkSize - chunkOverlap;  // 滑动窗口：前进 (512-64)=448 字
        }

        // 批量插入分块到 MySQL
        for (DocumentChunk chunk : chunks) {
            documentChunkMapper.insert(chunk);
        }

        log.info("文档分块完成: documentId={}, 总块数={}", documentId, chunks.size());
        return chunks.size();
    }
}
```

**实际测试结果**：
- 803字的TXT → 1块（不够512字，整块返回）
- 4567字的TXT → 5块（512×4 + 118最后一块）

### 5.6 upload() 方法完整流程

```java
@Override
public Document upload(MultipartFile file) {
    // ========== Step 1: 文件校验 ==========
    validateFile(file);

    String fileName = file.getOriginalFilename();
    String fileType = fileName.substring(fileName.lastIndexOf(".") + 1).toLowerCase();
    String title = fileName.substring(0, fileName.lastIndexOf("."));  // 去掉扩展名作为标题

    // ========== Step 2: 上传到 MinIO ==========
    String objectName = minioService.generateObjectName(fileName);
    minioService.uploadFile(file, objectName);

    // ========== Step 3: 构建 Document 元数据 ==========
    Document document = new Document();
    document.setUserId(1L);  // TODO: 后续从认证信息获取
    document.setTitle(title);
    document.setFileName(fileName);
    document.setFileType(fileType);
    document.setFileSize(file.getSize());
    document.setMinioPath(objectName);
    document.setChunkCount(0);  // 先设0，分块后更新
    document.setEmbeddingStatus(0);  // 0=待向量化入库

    // ========== Step 4: 存 MySQL 元数据 ==========
    // insert 后 document.id 会被自动填上 MySQL 生成的自增ID
    // 因为 Document.java 里有 @TableId(type = IdType.AUTO)
    documentMapper.insert(document);

    // ========== Step 5: 文档解析 ==========
    String fullText = documentParserService.parse(file, fileType);

    // ========== Step 6: 文本分块 + 存 MySQL ==========
    int chunkCount = documentChunkService.chunkAndSave(fullText, document.getId());

    // ========== Step 7: 更新文档的分块数 ==========
    document.setChunkCount(chunkCount);
    documentMapper.updateById(document);

    log.info("文档上传成功: id={}, title={}, chunks={}",
            document.getId(), document.getTitle(), chunkCount);

    return document;
}
```

### 6.3 EmbeddingService — 调用智谱 API 向量化

#### TODO 1：构建请求体 JSON

智谱 API 需要的请求体：
```json
{
  "model": "embedding-3",
  "input": ["文本1", "文本2"],
  "dimensions": 2048
}
```

**我的实现**：用 `LinkedHashMap` 构建，再由 Jackson 序列化为 JSON 字符串：

```java
Map<String, Object> body = new LinkedHashMap<>();
body.put("model", model);
body.put("input", texts);
body.put("dimensions", dimension);
String requestBody = objectMapper.writeValueAsString(body);
```

**为什么用 `LinkedHashMap` 而不是 `HashMap`？**
`HashMap` 不保证 key 的顺序，序列化出来的 JSON 字段顺序可能每次不同。`LinkedHashMap` 保持插入顺序，请求体字段顺序稳定（model → input → dimensions），调试时更直观，也避免某些 API 对字段顺序敏感的问题。

#### TODO 2：从响应 JSON 中提取向量（POJO 绑定）⭐ 面试亮点

智谱 API 返回的 JSON：
```json
{
  "data": [
    {"index": 0, "embedding": [0.12, 0.34, ...2048个]},
    {"index": 1, "embedding": [0.56, 0.78, ...]}
  ],
  "model": "embedding-3",
  "object": "list",
  "usage": {"prompt_tokens": 10, "total_tokens": 10}
}
```

**最初方案（脚手架给的）**：手动遍历 JsonNode + 双层 for 循环：

```java
// 方案A：手动遍历 — 代码冗长，且性能不好
List<float[]> vectors = new ArrayList<>();
for (JsonNode node : dataArray) {
    JsonNode embeddingNode = node.path("embedding");
    float[] vector = new float[embeddingNode.size()];
    for (int i = 0; i < embeddingNode.size(); i++) {
        vector[i] = (float) embeddingNode.get(i).asDouble();  // 逐个装箱拆箱
    }
    vectors.add(vector);
}
```

**我的优化方案**：用 Jackson POJO 绑定，定义两个 DTO 类，一次 `readValue` 搞定：

```java
// 方案B：POJO 绑定 — 简洁、类型安全、Jackson内部优化了数组转换
@Data
@JsonIgnoreProperties(ignoreUnknown = true)
static class EmbeddingResponse {
    private List<EmbeddingItem> data;
}

@Data
@JsonIgnoreProperties(ignoreUnknown = true)
static class EmbeddingItem {
    private int index;
    private float[] embedding;
}

// 使用：
EmbeddingResponse resp = objectMapper.readValue(response.getBody(), EmbeddingResponse.class);
List<float[]> vectors = resp.getData().stream()
        .map(EmbeddingItem::getEmbedding)
        .toList();
```

**两种方案对比**：

| 维度 | 方案A（手动遍历） | 方案B（POJO 绑定） |
|------|------------------|-------------------|
| 代码量 | 8行 + 嵌套循环 | 2行（readValue + stream） |
| 可读性 | 低（看到双层循环要想一下） | 高（一眼看出在做什么） |
| 可维护性 | 低（JSON 结构变了要改循环逻辑） | 高（改 DTO 字段就行） |
| 性能 | 低（逐个 asDouble 装箱拆箱） | 高（Jackson 内部直接反序列化 float[]） |
| 类型安全 | 低（运行时才知道类型对不对） | 高（编译期就检查类型） |

**面试怎么说**：
> "项目里调用智谱 Embedding API 时，最初脚手架给的是手动遍历 JsonNode 提取向量的方案——双层 for 循环逐个 `asDouble()` 再强转 float。我发现这个方案代码冗长且性能不好（逐个装箱拆箱），就改成了 Jackson 的 POJO 绑定方式：定义 `EmbeddingResponse` 和 `EmbeddingItem` 两个 DTO 类，用 `readValue` 一次性反序列化，再用 stream 的 `map` 提取 embedding 数组。代码从 8 行减到 2 行，可读性和性能都更好。"

#### `@JsonIgnoreProperties(ignoreUnknown = true)` ⭐ 面试亮点

**为什么需要这个注解？**

智谱 API 返回的 JSON 里有 `model`、`object`、`usage` 等字段，但我们的 `EmbeddingResponse` 只定义了 `data` 字段。Jackson 默认行为是：遇到 JSON 中有但 Java 类中没有的字段，抛 `UnrecognizedPropertyException`。

加上 `@JsonIgnoreProperties(ignoreUnknown = true)` 后，Jackson 会自动忽略未映射的字段，只反序列化我们关心的 `data`。

**面试怎么说**：
> "调用第三方 API 时，返回的 JSON 往往包含很多我们不需要的字段。如果用 Jackson POJO 绑定，默认遇到未映射字段会报错。我在 DTO 类上加了 `@JsonIgnoreProperties(ignoreUnknown = true)`，让 Jackson 自动忽略多余字段，这样即使 API 返回结构有变化（比如新增了字段），我们的代码也不会挂。这是调用第三方 API 的防御性编程实践。"

#### TODO 3：分批处理

智谱 API 一次最多处理 64 条文本。如果文档有 100 个文本块，需要分 2 批：

```java
for (int i = 0; i < texts.size(); i += BATCH_SIZE) {
    int end = Math.min(i + BATCH_SIZE, texts.size());
    List<String> batch = texts.subList(i, end);
    allVectors.addAll(embedBatch(batch));
}
```

**关键点**：
- `i += BATCH_SIZE`：每次跳 64 条
- `Math.min(i + BATCH_SIZE, texts.size())`：最后一批可能不足 64 条，取实际剩余数量
- `subList(i, end)`：左闭右开区间，截取当前批次的文本
- `allVectors.addAll()`：每批的向量按顺序追加到总列表

**为什么要分批？**
API 有调用限制（rate limit），一次传太多会报 429 Too Many Requests。64 条是智谱 API 的单次上限。

### 6.4 MilvusService — 向量数据库操作

#### TODO 4：定义 Collection Schema

Milvus 的 Collection 相当于 MySQL 的表，建表时需要定义字段：

```java
FieldType idField = FieldType.newBuilder()
        .withName("id")
        .withDataType(DataType.Int64)
        .withPrimaryKey(true)
        .withAutoID(false)        // 不自动生成ID，用MySQL的chunk id
        .build();
FieldType documentIdField = FieldType.newBuilder()
        .withName("document_id")
        .withDataType(DataType.Int64)
        .build();
FieldType contentField = FieldType.newBuilder()
        .withName("content")
        .withDataType(DataType.VarChar)
        .withMaxLength(2048)      // 变长字符串，最大2048字节
        .build();
FieldType embeddingField = FieldType.newBuilder()
        .withName("embedding")
        .withDataType(DataType.FloatVector)
        .withDimension(dimension) // 2048维，和智谱API输出一致
        .build();

CollectionSchemaParam schema = CollectionSchemaParam.newBuilder()
        .withFieldTypes(List.of(idField, documentIdField, contentField, embeddingField))
        .build();

CreateCollectionParam createParam = CreateCollectionParam.newBuilder()
        .withCollectionName(collectionName)
        .withSchema(schema)
        .build();
```

**4个字段的作用**：

| 字段 | 类型 | 作用 |
|------|------|------|
| `id` | Int64 (主键) | 对应 MySQL document_chunk.id，建立 MySQL↔Milvus 的关联 |
| `document_id` | Int64 | 所属文档ID，用于按文档过滤搜索范围 |
| `content` | VarChar(2048) | 文本内容，搜索时直接返回，省去再查 MySQL |
| `embedding` | FloatVector(2048) | 向量字段，核心字段，用于相似度搜索 |

**为什么 `withAutoID(false)`？**
因为我们要用 MySQL document_chunk 表的自增 ID 作为 Milvus 的主键，这样向量搜索找到 chunkId 后可以直接回 MySQL 查完整信息。如果让 Milvus 自动生成 ID，就无法和 MySQL 关联了。

**分块大小 512 vs content 字段 maxLength 2048 vs 向量维度 2048——三个数字含义不同**：
- **512**：文本分块时的字符数上限（`rag.chunk-size`），每块最多 512 个字符
- **2048（maxLength）**：Milvus 中 VarChar 字段的存储容量上限。512 字符的中文 UTF-8 编码最多 1536 字节，所以 2048 留了余量
- **2048（dimension）**：智谱 embedding-3 模型输出的向量维度，和分块大小无关

#### 索引创建与加载

建完 Collection 后，需要创建索引和加载到内存：

```java
CreateIndexParam createIndexParam = CreateIndexParam.newBuilder()
        .withCollectionName(collectionName)
        .withFieldName("embedding")
        .withIndexType(IndexType.IVF_FLAT)     // 索引类型
        .withMetricType(MetricType.COSINE)     // 相似度度量
        .withExtraParam("{\"nlist\":1024}")    // 聚类中心数
        .build();
milvusServiceClient.createIndex(createIndexParam);

milvusServiceClient.loadCollection(
        LoadCollectionParam.newBuilder()
                .withCollectionName(collectionName)
                .build());
```

**IVF_FLAT 索引**：把向量空间分成 `nlist`（1024）个聚类，搜索时只扫描最相似的 `nprobe` 个聚类，加速搜索。FLAT 表示聚类内部用暴力计算（精确）。

**为什么用 COSINE（余弦相似度）而不是 L2（欧氏距离）？**
文本向量的语义相似度看的是"方向"而不是"距离"。两段文本即使向量长度不同（表达强度不同），只要方向一致（语义相似），余弦相似度就高。L2 受向量长度影响，不适合文本语义搜索。

**`loadCollection` 的作用**：Milvus 的数据存在磁盘上，搜索前必须加载到内存。类似 MySQL 的 InnoDB Buffer Pool。

#### 向量插入（FastJSON vs Gson）⭐ 踩坑记录

Milvus SDK 2.4.x 内部使用阿里巴巴 FastJSON（`com.alibaba.fastjson.JSONObject`），**不是** Google Gson（`com.google.gson.JsonObject`）。两者 API 不兼容：

| 操作 | Gson | FastJSON |
|------|------|----------|
| 创建对象 | `new JsonObject()` | `new JSONObject()` |
| 添加字符串 | `addProperty("key", "value")` | `put("key", "value")` |
| 添加数字 | `addProperty("key", 123)` | `put("key", 123)` |
| 添加数组 | `new JsonArray()` + `add()` | `new JSONArray()` + `add()` |
| import 包 | `com.google.gson.*` | `com.alibaba.fastjson.*` |

**实际代码**（用 FastJSON）：

```java
List<JSONObject> rows = new ArrayList<>();
for (int i = 0; i < chunkIds.size(); i++) {
    JSONObject row = new JSONObject();
    row.put("id", chunkIds.get(i));
    row.put("document_id", documentId);
    row.put("content", contents.get(i));

    JSONArray vectorArray = new JSONArray();
    for (float v : vectors.get(i)) {
        vectorArray.add(v);
    }
    row.put("embedding", vectorArray);

    rows.add(row);
}
```

**面试怎么说**：
> "我在写 Milvus 向量插入时遇到了一个编译错误——脚手架代码用的是 Gson 的 JsonObject，但 Milvus SDK 2.4.x 内部用的是阿里巴巴 FastJSON 的 JSONObject，两者 API 不兼容。Gson 用 `addProperty()`，FastJSON 用 `put()`。我通过看编译错误信息中的类型签名发现了这个问题，把 Gson API 全部替换成 FastJSON API 后解决。这让我学到：引入第三方 SDK 时要注意它的传递依赖可能和项目已有的库冲突。"

### 6.5 DocumentServiceImpl.embed() — 串联全流程

`embed()` 方法是把 EmbeddingService 和 MilvusService 串起来的"指挥官"：

```java
@Override
public void embed(Long id) {
    // ===== TODO 6: 查文档 + 幂等检查 =====
    Document document = documentMapper.selectById(id);
    if (document == null) {
        throw new BusinessException("文档不存在");
    }
    if (document.getEmbeddingStatus() == 1) {
        throw new BusinessException("文档已向量化");
    }

    // ===== TODO 7: 查文本块列表 =====
    LambdaQueryWrapper<DocumentChunk> wrapper = new LambdaQueryWrapper<>();
    wrapper.eq(DocumentChunk::getDocumentId, id)
           .orderByAsc(DocumentChunk::getChunkIndex);  // 按顺序排
    List<DocumentChunk> chunks = documentChunkMapper.selectList(wrapper);
    if (chunks.isEmpty()) {
        throw new BusinessException("文档没有文本块，请先上传并解析");
    }

    // ===== TODO 8: 提取文本 → Embedding → 存Milvus =====
    List<String> texts = chunks.stream().map(DocumentChunk::getContent).toList();
    List<float[]> vectors = embeddingService.embed(texts);
    List<Long> chunkIds = chunks.stream().map(DocumentChunk::getId).toList();
    milvusService.insertVectors(chunkIds, id, texts, vectors);

    // ===== TODO 9: 更新文档状态 =====
    document.setEmbeddingStatus(1);  // 1=已完成
    documentMapper.updateById(document);
    log.info("向量化完成: id={}, chunkCount={}", id, chunks.size());
}
```

#### 幂等检查 ⭐ 面试亮点

**为什么要检查 `embeddingStatus == 1`？**
防止重复向量化。如果用户点了两次"向量化"按钮，或者网络重试，不应该重复调用 Embedding API（费钱）和重复插入 Milvus（数据冗余）。

**面试怎么说**：
> "embed() 方法第一步就做了幂等检查——如果文档的 embeddingStatus 已经是 1（已向量化），直接抛异常拒绝重复执行。这样即使用户重复点击或网络重试，也不会重复调用付费的 Embedding API，也不会往 Milvus 里插入重复向量。"

#### Stream API 数据转换

三个 `stream().map().toList()` 把 List\<DocumentChunk\> 转成不同类型的 List：

```java
List<String> texts = chunks.stream().map(DocumentChunk::getContent).toList();   // 提取文本
List<float[]> vectors = embeddingService.embed(texts);                          // 文本→向量
List<Long> chunkIds = chunks.stream().map(DocumentChunk::getId).toList();       // 提取ID
```

**方法引用 `DocumentChunk::getContent`**：等价于 `chunk -> chunk.getContent()`，更简洁。

**顺序保证**：`texts`、`vectors`、`chunkIds` 三个列表的下标一一对应。`chunks` 用 `orderByAsc(chunkIndex)` 保证了原始顺序，stream 操作不改变顺序，所以 `texts[0]` 对应 `vectors[0]` 对应 `chunkIds[0]`。

#### `@PostConstruct` 自动建表

```java
@PostConstruct
public void init() {
    try {
        ensureCollection();
    } catch (Exception e) {
        log.warn("Milvus初始化失败（可能Milvus还没启动）: {}", e.getMessage());
    }
}
```

`@PostConstruct` 表示"Bean 创建完成后自动执行"。Spring 启动时创建 MilvusService Bean → 自动调 init() → 调 ensureCollection() → 建表+建索引+加载。

**为什么 catch 住异常只 warn 不 throw？** 因为 Milvus 可能还没启动（Docker 容器还没就绪），不应该让整个应用启动失败。等 Milvus 启动后，用户手动调 embed() 时会触发建表（但当前代码只在 @PostConstruct 建表，这是个可以优化的点）。

### 6.6 Milvus v1 vs v2 API ⭐ 踩坑记录

Milvus Java SDK 2.4.x 同时存在两套 API：

| 维度 | v1 API | v2 API |
|------|--------|--------|
| 包名 | `io.milvus.client.*` / `io.milvus.param.*` | `io.milvus.v2.*` |
| 客户端 | `MilvusServiceClient` | `MilvusClientV2` |
| Builder | `newBuilder().withXxx()` | `builder().xxx()` |
| 索引参数 | `IndexParam.newBuilder().withXxx()` | `IndexParam.builder().xxx()` |
| 创建索引 | `CreateIndexParam.newBuilder().withIndexParams()` | `CreateIndexReq.builder()` |

**本项目用 v1 API**（`MilvusServiceClient` + `newBuilder().withXxx()`），因为 v2 API 在 2.4.x 还不完全稳定。

**踩坑经历**：最初 import 了 `io.milvus.v2.common.IndexParam`（v2），但 `CreateIndexParam` 是 v1 的，导致编译错误。修复方法：删掉 v2 import，统一用 v1 的 `io.milvus.param.*`。

**面试怎么说**：
> "我在用 Milvus SDK 时发现它同时存在 v1 和 v2 两套 API，包名和 Builder 方法都不同。v1 用 `newBuilder().withXxx()`，v2 用 `builder().xxx()`。如果同一个文件里混用两套 API 会编译报错。我通过查看 import 包名区分版本，统一使用 v1 API 解决了问题。这让我认识到：使用第三方库时要先确认版本，不同版本 API 可能差异很大。"

### 6.7 Milvus standalone 模式 bug

**解决方案**：放弃 standalone 模式，改用多容器模式——单独启动 etcd + milvus-minio + milvus 三个容器，各自独立运行。虽然多占了端口和内存，但稳定。

### 8.3 Markdown 渲染与 XSS 防护（TODO 1）

DeepSeek 输出天然是 Markdown 格式（`##` 标题、`-` 列表、```` ``` ```` 代码块），直接用 `{{ }}` 显示是一坨纯文本。

```js
const md = new MarkdownIt({
  html: false,    // 禁止原始 HTML 标签（防 XSS）
  breaks: true,   // 换行符 → <br>
  linkify: true,  // 自动识别 URL
})

function renderMarkdown(content) {
  return md.render(content || '')
}
```

模板中用 `v-html="renderMarkdown(msg.content)"` 渲染。

**为什么 `html: false`？**
大模型可能输出 `<script>alert('xss')</script>` 这样的内容。`html: false` 会让 markdown-it 把 HTML 标签当纯文本转义（`<` → `&lt;`），防止 XSS。

**`v-html` 的安全风险？**
`v-html` 会把字符串当 HTML 插入 DOM，如果内容含恶意脚本就会执行。所以用 `v-html` 前必须确保内容已过滤（markdown-it 的 `html: false` 就是这层防护）。

### 8.4 自动滚动 + nextTick（TODO 2）

AI 回答很长，新消息会超出可视区域。不自动滚动，用户看不到最新回答。

```js
watch(messages, () => {
  nextTick(() => {
    const el = messageContainer.value
    if (el) el.scrollTop = el.scrollHeight
  })
}, { deep: true })
```

**为什么用 `nextTick`？**
Vue 更新 DOM 是异步的（批量更新机制）。`messages.value.push(...)` 之后，DOM 还没更新，直接读 `scrollHeight` 拿到的是旧高度。`nextTick` 等待 DOM 更新完成后再滚动。

**为什么 `deep: true`？**
`messages` 是数组，`push` 不会改变数组引用地址，浅层 watch 监听不到。`deep: true` 让 Vue 递归监听数组内部变化。

### 8.5 路由监听 — 同组件复用问题（TODO 3）

**问题**：用户在侧边栏从会话3切到会话5，URL 从 `/chat/3` 变成 `/chat/5`，但 ChatView 组件**没有销毁重建**（Vue Router 对同一路由组件会复用），`onMounted` 不会再次触发，导致历史不刷新。

```js
watch(() => route.params.sessionId, async (newId) => {
  if (newId) {
    const res = await getHistory(newId)

  } else {

  }
})

**为什么 `watch` 的第一个参数是函数？**
`watch` 可以监听两种东西：`ref` / `reactive` 对象，或者一个 getter 函数。`route.params.sessionId` 不是响应式 ref，需要用函数形式 `() => route.params.sessionId` 让 Vue 每次重新求值并比较。

async function deleteSession(id) {
  try {
    await ElMessageBox.confirm('确定删除这个会话？删除后不可恢复。', '提示', {
      type: 'warning',
      confirmButtonText: '删除',
      cancelButtonText: '取消',
    })
    await chatStore.deleteSession(id)
    ElMessage.success('删除成功')
    if (router.currentRoute.value.params.sessionId == id) {
      router.push('/chat')
    }
  } catch (e) {
    if (e !== 'cancel') console.warn('删除失败', e)
  }
}
```

**`@click.stop` 的作用？**
删除图标在会话项内部，点击删除图标时事件会冒泡到父元素，同时触发 `switchSession`。`@click.stop` 阻止事件冒泡，确保只执行删除逻辑。

**为什么 `catch` 里不报错？**
`ElMessageBox.confirm` 用户点"取消"也会 reject Promise 进入 catch，这不是错误，不应该报错。只有 `e !== 'cancel'` 时才是真正的删除失败。

## 十、面试亮点：我在项目中做的优化

> 这一节专门记录"你可以说'这是我主动优化的'"的内容。面试官喜欢听的不是"我实现了什么功能"，而是"我遇到什么问题、怎么思考、怎么解决的"。

### 亮点1：JSON解析从手动遍历优化为POJO绑定

**场景**：解析智谱 Embedding API 的响应，提取向量数组。

**最初方案**（脚手架给的）：手动遍历 `JsonNode`，双层 for 循环逐个 `asDouble()` 再强转 float——8行代码，性能差（逐个装箱拆箱），可读性低。

**我的优化**：定义 `EmbeddingResponse` 和 `EmbeddingItem` 两个 DTO 类，用 Jackson 的 `readValue` 一次性反序列化，再用 `stream().map()` 提取——2行代码，类型安全，Jackson 内部优化了数组转换。

**面试话术**：
> "我在解析第三方 API 响应时，最初脚手架给的是手动遍历 JsonNode 的双层 for 循环方案。我发现这个方案代码冗长、可读性差，而且逐个 `asDouble()` 有装箱拆箱开销。于是我改成了 Jackson POJO 绑定方式：定义 DTO 类，一次 `readValue` 反序列化，再 stream 提取。代码量从 8 行减到 2 行，可读性和性能都更好。这个经历让我意识到，拿到框架代码不能直接用，要想一想有没有更优解。"

**追问预案**：
- "POJO绑定比手动遍历快多少？" → Jackson 内部用反射批量设置字段值，比逐个 asDouble() 调用少很多次方法调用和类型转换
- "如果API返回结构经常变怎么办？" → DTO 类加 `@JsonIgnoreProperties(ignoreUnknown = true)`，多余字段自动忽略，只要我们关心的字段不变就不受影响
- "stream().map().toList()会不会乱序？" → 不会。Stream 的 map 操作保持元素顺序，`toList()` 收集成 List 也保持顺序。只有 `parallelStream` 才可能乱序

### 亮点2：@JsonIgnoreProperties 防御第三方API变更

**场景**：智谱 API 返回的 JSON 包含 `model`、`object`、`usage` 等字段，但我们的 DTO 只定义了 `data`。

**问题**：Jackson 默认遇到未映射字段抛 `UnrecognizedPropertyException`。

**解决**：DTO 类加 `@JsonIgnoreProperties(ignoreUnknown = true)`，自动忽略多余字段。

**面试话术**：
> "调用第三方 API 时，返回结构往往包含很多我们不需要的字段。如果用 POJO 绑定，Jackson 默认遇到未映射字段会报错。我在 DTO 上加了 `@JsonIgnoreProperties(ignoreUnknown = true)`，让 Jackson 自动忽略多余字段。这样即使 API 新增了字段，我们的代码也不会挂。这是调用第三方 API 的防御性编程实践。"

### 亮点3：用LinkedHashMap保证JSON字段顺序

**场景**：构建智谱 API 的请求体 JSON。

**问题**：用 `HashMap` 构建请求体时，key 的顺序不确定，序列化出的 JSON 字段顺序每次可能不同。

**解决**：改用 `LinkedHashMap`，保持插入顺序（model → input → dimensions），调试时更直观。

**面试话术**：
> "构建请求体 JSON 时我用了 LinkedHashMap 而不是 HashMap。HashMap 不保证 key 顺序，虽然 JSON 规范不关心字段顺序，但用 LinkedHashMap 保证顺序稳定，调试时更容易对照 API 文档检查。"

### 亮点4：幂等设计防止重复向量化

**场景**：用户可能重复点击"向量化"按钮，或网络重试触发重复请求。

**解决**：embed() 方法第一步检查 `embeddingStatus == 1`，已向量化则直接拒绝。

**面试话术**：
> "embed() 方法第一步就做了幂等检查。如果文档已经向量化过（status=1），直接抛异常拒绝。这样即使用户重复点击或网络重试，也不会重复调用付费的 Embedding API，也不会往 Milvus 插入重复向量。幂等设计在生产环境中很重要，尤其是涉及付费 API 和数据写入的场景。"

**追问预案**：
- "如果向量化中途失败了怎么办？" → 目前 status 还是 0（未完成），用户可以重新触发。但缺点是没有记录"失败"状态。生产环境可以加一个 status=2（失败）+ 失败原因字段，或者用状态机（待处理→处理中→完成/失败）
- "能不能用数据库唯一约束做幂等？" → 可以用 `document_id` + `chunk_id` 做 Milvus 的唯一约束（upsert 语义），但 Milvus 2.4 的 upsert 支持有限，所以用应用层状态检查更实际

### 亮点5：解决Milvus SDK的Gson/FastJSON依赖冲突

**场景**：Milvus 向量插入时，脚手架代码用 Gson 的 `JsonObject`，但编译报错。

**排查过程**：看编译错误信息——`List<com.google.gson.JsonObject>` 无法转换为 `List<com.alibaba.fastjson.JSONObject>`。发现 Milvus SDK 2.4.x 内部用的是 FastJSON 不是 Gson。

**解决**：把 Gson API 全部替换成 FastJSON API（`JsonObject`→`JSONObject`，`addProperty`→`put`）。

**面试话术**：
> "我在写 Milvus 向量插入时遇到编译错误。看错误信息发现类型签名里一个是 `com.google.gson.JsonObject`，一个是 `com.alibaba.fastjson.JSONObject`——原来 Milvus SDK 2.4.x 内部用 FastJSON 而不是 Gson。我把 Gson API 全部替换成 FastJSON API 后解决。这让我学到：引入第三方 SDK 时要注意它的传递依赖可能和项目已有库冲突，遇到编译错误时先看类型签名能快速定位问题。"

### 亮点6：解决Milvus v1/v2 API混用

**场景**：import 了 `io.milvus.v2.common.IndexParam`（v2），但 `CreateIndexParam` 是 v1 的，编译报错。

**排查过程**：Milvus SDK 2.4.x 同时存在 v1 和 v2 两套 API，包名和 Builder 方法都不同。v1 用 `newBuilder().withXxx()`，v2 用 `builder().xxx()`。

**解决**：删掉 v2 import，统一用 v1 的 `io.milvus.param.*`。

**面试话术**：
> "Milvus Java SDK 2.4.x 同时存在 v1 和 v2 两套 API，包名和 Builder 风格都不同。我最初混用了两套 API 导致编译错误，通过查看 import 包名区分版本后统一为 v1 API。这个经历让我认识到：使用第三方库时要先确认版本对应的 API 风格，看官方文档时也要注意版本号。"

### 亮点7：RestTemplate和ObjectMapper改为@Bean注入

**场景**：最初在 EmbeddingService 和 LlmService 中直接 `new RestTemplate()` 和 `new ObjectMapper()`，后来重构为 Spring 容器管理。

**重构前**：
```java
private final RestTemplate restTemplate = new RestTemplate();
private final ObjectMapper objectMapper = new ObjectMapper();
```

**重构后**：
```java
// RestTemplateConfig.java — 统一配置
@Bean
public RestTemplate restTemplate(RestTemplateBuilder builder) {
    return builder
            .setConnectTimeout(Duration.ofSeconds(10))
            .setReadTimeout(Duration.ofSeconds(60))
            .build();
}

// EmbeddingService.java / LlmService.java — 构造注入
@RequiredArgsConstructor
@Service
public class EmbeddingService {
    private final RestTemplate restTemplate;   // Spring自动注入
    private final ObjectMapper objectMapper;   // Spring Boot自动配置
}
```

**为什么要改？三个理由（面试重点）**：

| 理由 | 说明 |
|------|------|
| **超时控制** | 裸 `new RestTemplate()` 没有超时设置，调第三方API时如果对方不响应，线程会一直阻塞。@Bean统一设置连接10s+读取60s |
| **可测试性** | @Bean创建的对象在单元测试时可以用 `@MockBean` 替换，而 `new` 出来的对象无法被Spring替换 |
| **ObjectMapper自动配置** | Spring Boot自动配置的ObjectMapper已注册Java8时间模块、默认关闭 `FAIL_ON_UNKNOWN_PROPERTIES`。自己 `new` 的什么都没有，所以DTO才需要手动加 `@JsonIgnoreProperties` |

**面试话术**：
> "项目初期为了快速开发，在Service里直接 new RestTemplate 和 ObjectMapper。后来发现两个问题：一是 RestTemplate 没有超时设置，调第三方API可能线程阻塞；二是自己 new 的 ObjectMapper 丢失了 Spring Boot 的自动配置（比如 Java8 时间模块和容错策略），导致每个DTO都要手动加 @JsonIgnoreProperties。于是抽了一个 RestTemplateConfig，用 @Bean + RestTemplateBuilder 统一管理，Service 改用 @RequiredArgsConstructor 构造注入。"

**追问预案**：

- **Q: 为什么 ObjectMapper 不需要自己写 @Bean？**
  A: Spring Boot 的 JacksonAutoConfiguration 已经自动注册了一个 ObjectMapper Bean，包含了 JavaTimeModule、默认关闭 FAIL_ON_UNKNOWN_PROPERTIES 等配置。直接 @Autowired 或构造注入就能拿到这个配置好的实例。

- **Q: @RequiredArgsConstructor 怎么做到只注入 final 字段？**
  A: Lombok 的 @RequiredArgsConstructor 只为 `final` 字段和 `@NonNull` 字段生成构造函数参数。@Value 注入的字段不是 final（Spring在构造后通过反射注入），所以不会进构造函数。Spring 看到唯一的构造函数就自动用它做依赖注入。

- **Q: 为什么不直接在字段上加 @Autowired？**
  A: Spring 官方推荐构造注入而非字段注入。原因：构造注入保证依赖不可变（final）、依赖一目了然（构造函数签名就是依赖清单）、不需要 Spring 容器也能 new 对象做单元测试（直接传 Mock 对象）。

### 亮点8：RAG在线流程编排 — 先存问题再做后续

**场景**：ChatServiceImpl.ask() 方法编排整个RAG在线流程（存问题→向量化→检索→拼接→生成→存回答）。

**关键设计**：用户问题先存到数据库，再做后续的向量化/检索/大模型调用。

```java
// 第一步就是存用户问题，不是最后才存
ChatMessage userMsg = new ChatMessage();
userMsg.setSessionId(sessionId);
userMsg.setRole("user");
userMsg.setContent(question);
chatMessageMapper.insert(userMsg);  // ← 先存，即使后面崩了也有记录

// 然后才是向量化、检索、生成...
List<float[]> vectors = embeddingService.embed(List.of(question));
```

**为什么这么设计？**
- 向量化调智谱API可能失败、检索Milvus可能超时、大模型可能限流
- 如果最后才存，中间任何一步失败，用户的问题就丢了
- 先存 = 数据优先，保证可追溯

**面试话术**：
> "在RAG在线流程中，我把保存用户问题放在最前面，而不是和助手回答一起存。因为后续的向量化、向量检索、大模型调用都是网络IO，任何一步都可能失败。如果最后才存，中间崩溃用户问题就丢了。先存保证即使后续流程失败，用户的问题记录也保留——这是数据优先的设计原则。"

**追问预案**：

- **Q: 如果向量化失败了，用户问题已经存了但没有回答，怎么办？**
  A: 前端可以检测到该消息没有对应的assistant回答（role=user但没有后续role=assistant），显示"回答失败，请重试"按钮。后端也可以加一个定时任务，扫描有问无答的记录，自动重试。

- **Q: 为什么不把整个ask方法加@Transactional？**
  A: 向量化、检索、大模型调用都是远程网络IO，耗时可能几秒到几十秒。放在一个事务里会长时间占用数据库连接，影响其他请求。RAG流程更适合用"最终一致性"而不是强事务——先存问题，成功后存回答，失败就部分存储。

- **Q: sources字段为什么用JSON字符串而不是关联表？**
  A: sources是检索结果的快照（当时检索到的chunkId+score+预览），如果用关联表，文档删除后来源就丢了。JSON字符串保证回答和来源是一个整体，不可变。

---

### 亮点9：Markdown渲染的XSS防护与前端交互细节

**场景**：DeepSeek 输出是 Markdown 格式，需要用 `markdown-it` 渲染成 HTML 再用 `v-html` 插入 DOM。但 `v-html` 会执行 HTML 标签，如果大模型输出 `<script>` 标签就会导致 XSS。

**我的方案**：
```js
const md = new MarkdownIt({
  html: false,    // 关键：禁止原始 HTML 标签
  breaks: true,
  linkify: true,
})
```

`html: false` 让 markdown-it 把所有 HTML 标签当纯文本转义（`<` → `&lt;`），即使大模型输出 `<script>alert('xss')</script>` 也只会显示成文字，不会执行。

**面试话术**：
> "AI 回答用 markdown-it 渲染成 HTML，通过 `v-html` 插入 DOM。但 `v-html` 有 XSS 风险——如果大模型输出 `<script>` 标签就会被执行。我在初始化 markdown-it 时设了 `html: false`，把所有原始 HTML 标签转义成纯文本，在渲染层就阻断了 XSS 注入路径。这是纵深防御思路：即使大模型被 prompt injection 诱导输出恶意标签，前端也能兜底。"

**追问预案**：

- **Q: `html: false` 会不会影响正常 Markdown 渲染？**
  A: 不会。`html: false` 只禁止原始 HTML 标签，Markdown 语法（`##`、`-`、```` ``` ````）正常渲染。markdown-it 会把这些语法转成安全的 HTML 标签（`<h2>`、`<ul>`、`<pre><code>`），这些是 markdown-it 自己生成的，不是用户输入的，不存在 XSS 风险。

- **Q: 如果用户需要看 HTML 标签原文呢？**
  A: markdown-it 会把 `<script>` 转义成 `&lt;script&gt;` 显示在页面上，用户看到的是文本"<script>"，不是执行结果。这正好符合预期——展示原文，不执行代码。

- **Q: 除了 XSS，还做了哪些前端安全措施？**
  A: 删除会话用 `ElMessageBox.confirm` 二次确认防误删；API 请求通过 Axios 拦截器统一处理 401/403；后端用 Spring 全局异常处理 `@RestControllerAdvice` 兜底，不会把堆栈信息泄露给前端。

## 十一、开发者问题解决方法论

> **核心认知：没有程序员靠脑子里记住所有API来写代码。真正的技能是"知道怎么找到答案"。**

### 7.1 新手的困惑 vs 高手的方法

| 新手心态 | 高手心态 |
|---------|---------|
| "我怎么知道有这个类？" | "我需要什么功能，去查哪个库能提供" |
| "我要记住所有API" | "记住模式，不记API。用的时候查文档" |
| "遇到不认识的类就慌" | "不认识的类 → 看import → 搜索 → 读文档" |
| "AI帮我写了我就抄" | "AI帮找方向 → 我自己理解 → 我自己写" |

### 7.2 五步问题解决法（万能公式）

遇到任何"不知道怎么实现"的功能，按这个流程走：

```
第1步：用自然语言描述你要做什么
       → "我要把用户上传的文件存到MinIO里"

第2步：搜索关键词
       → Google/Bing/AI："Java MinIO 上传文件"
       → 或直接看官方文档

第3步：找到示例代码，理解核心API
       → 文档/搜索结果会给你示例
       → 重点看：需要创建什么对象？调用什么方法？传什么参数？

第4步：照着示例写，但自己理解每一行
       → 不要无脑复制
       → 问自己：这行为什么要这样写？去掉会怎样？

第5步：跑起来，报错了看错误信息
       → 编译错误 → 看提示缺什么import
       → 运行错误 → 看异常堆栈，搜索报错信息
```

### 7.3 信息渠道优先级（从可靠到便捷）

| 优先级 | 渠道 | 什么时候用 | 示例 |
|--------|------|-----------|------|
| ⭐⭐⭐⭐⭐ | **官方文档** | 需要准确API和用法 | min.io/docs/minio/linux/developers/java |
| ⭐⭐⭐⭐ | **项目已有代码** | 同项目里有类似功能可参考 | 写ChatService前先看DocumentServiceImpl怎么写的 |
| ⭐⭐⭐⭐ | **搜索引擎** | 找具体问题的解决方案 | "Spring Boot MultipartFile 文件上传" |
| ⭐⭐⭐ | **AI助手（包括我）** | 找方向、理解概念、debug | "MinIO上传文件需要哪些参数？" |
| ⭐⭐ | **Stack Overflow** | 看别人遇到同类问题怎么解决的 | 搜索具体报错信息 |
| ⭐ | **博客/教程** | 入门理解，但可能过时 | 仅供参考，以官方文档为准 |

### 7.4 用项目里的真实例子演示

#### 例子1：实现 MinIO 文件上传

**我的真实思考过程（不是事后编的）：**

```
第1步：描述需求
  "把用户上传的文件存到MinIO对象存储里"

第2步：搜索
  → 搜索 "MinIO Java SDK"
  → 找到官方文档：https://min.io/docs/minio/linux/developers/java/minio-java.html
  → 文档第一段就说了：用 MinioClient.builder() 创建客户端

第3步：看示例代码
  文档里的示例：
  MinioClient minioClient = MinioClient.builder()
      .endpoint("https://play.min.io")
      .credentials("accessKey", "secretKey")
      .build();
  minioClient.uploadObject(
      UploadObjectArgs.builder()
          .bucket("my-bucket")
          .object("my-object")
          .filename("my-file")
          .build());

第4步：理解并改造
  → endpoint 从配置文件读（不写死）
  → credentials 从配置文件读（密码不进代码）
  → bucket 用我们项目的 "rag-documents"
  → 用 InputStream 而不是 filename（因为用户上传的是MultipartFile，不是本地文件）

第5步：改造后查API确认
  → 搜索 "MinIO Java uploadObject InputStream"
  → 发现应该用 putObject() 而不是 uploadObject()
  → putObject 接受 InputStream 参数
```

**关键点**：我不是"知道"有 `MinioClient` 这个类的，我是查到的。你也能查到。

#### 例子2：实现 PDF 文本提取

```
第1步：描述需求
  "从PDF文件里提取出纯文本内容"

第2步：搜索
  → "Java PDF 提取文本"
  → 搜索结果：Apache PDFBox、iText、PDFBox 最常用

第3步：选库 + 看文档
  → PDFBox 是 Apache 官方的，免费开源，文档全
  → Maven 坐标：org.apache.pdfbox:pdfbox:2.0.27
  → 官方文档示例：PDDocument.load(file) → PDFTextStripper().getText(doc)

第4步：理解
  → PDDocument = 整个PDF文档的对象表示
  → PDFTextStripper = 文本提取器
  → getText() 返回纯文本字符串

第5步：自己写
  PDDocument document = PDDocument.load(inputStream);
  PDFTextStripper stripper = new PDFTextStripper();
  String text = stripper.getText(document);
  document.close();
```

#### 例子3：遇到报错不知道怎么办

```
场景：启动报错 "Failed to configure a DataSource"

第1步：读错误信息
  → "Failed to configure a DataSource" = 数据源配置失败
  → "url not specified" = 数据库URL没配

第2步：检查
  → 打开 application.yml
  → 看 datasource 配置块
  → 发现 url 配置写对了，但密码可能不对

第3步：搜索
  → 搜索 "Spring Boot Failed to configure a DataSource url not specified"
  → Stack Overflow 上有人说：检查 application.yml 缩进
  → 发现是 yml 缩进错了，url 和 username 没在 spring.datasource 下面

第4步：修复 → 重启 → 搞定
```

### 7.5 关于用AI的正确姿势

AI 是工具，不是拐杖。区别在于：

| ❌ 错误用法（依赖型） | ✅ 正确用法（辅助型） |
|---------------------|---------------------|
| "帮我写一个文件上传功能" | "Java里操作MinIO需要用什么库？核心API是什么？" |
| 直接复制AI生成的代码 | AI给方向 → 自己查文档 → 自己写 |
| 不看代码内容，能跑就行 | 逐行理解，问AI解释不懂的部分 |
| 遇到报错直接贴给AI | 先自己读错误信息，尝试理解，再问AI |

**判断标准**：关掉AI，你能不能：
1. 说出这段代码的思路？（能 = 你理解了）
2. 在白板上写出大致框架？（能 = 你掌握了）
3. 回答别人"为什么这么写"？（能 = 你真正学会了）

# RAG 知识库项目技术架构说明

> 本文是 RAG 知识库的**评估语料之一**，同时可作为项目技术说明使用。
> 与《Java 后端知识笔记》共同构成 `docs/eval/questions.json` 的检索语料。
> 文中所有参数均取自 `backend/src/main/resources/application.yml` 与源码实际实现。

## 一、整体架构

### 1.1 为什么选模块化单体

本项目采用**模块化单体（Modular Monolith）**架构，而不是微服务。理由有三条：

第一，交付场景匹配。项目面向央国企内部知识库这类场景，部署环境往往是单机或有限节点，
团队规模小、没有专职的运维与 SRE。微服务带来的注册中心、配置中心、链路追踪、容器编排
等基础设施成本，在这个场景下是净负债而非资产。

第二，**演进路径**清晰。模块化单体强制按业务边界分包（auth / document / chat / agent / rag），
模块之间只通过接口（Service 接口）+ DTO 交互，不跨模块直接访问对方 Mapper。
一旦某个模块（比如 rag 检索）真的成为性能瓶颈，可以按其边界整体拆出去变成独立服务——
此时因为边界已经画好，拆分成本远低于从「面条式单体」重构。

第三，一致性与事务简单。文档入库涉及 MinIO 对象、MySQL 元数据与分块、Milvus 向量三处写入，
单进程内可以用本地事务 + 补偿逻辑处理；拆成微服务后会直接引入分布式事务问题，
在这个业务规模下属于自找麻烦。

### 1.2 模块划分与职责

| 模块 | 包路径 | 职责 |
|------|--------|------|
| auth | `com.liushuwen.rag.auth` | 注册、登录、JWT 签发、当前用户 |
| document | `com.liushuwen.rag.document` | 文件存储、解析、分块、向量化、Milvus 读写 |
| chat | `com.liushuwen.rag.chat` | 会话管理、问答链路编排、LLM 调用 |
| rag | `com.liushuwen.rag.rag` | 查询改写、Rerank、意图路由、反思评审、长期记忆 |
| agent | `com.liushuwen.rag.agent` | 工具抽象与注册、ReAct 执行器、多 Agent 编排、熔断、指标 |
| common | `com.liushuwen.rag.common` | 统一响应体、业务异常、全局异常处理、用户上下文 |
| config | `com.liushuwen.rag.config` | JWT、Milvus、MinIO、MyBatis-Plus、RestTemplate、跨域配置 |
| eval | `com.liushuwen.rag.eval` | 检索质量评估入口 |

### 1.3 跨模块调用约定

**跨模块调用一律走 Service 接口**，禁止直接注入对方的 Mapper 或实现类。
例如 chat 模块需要读文档信息时，注入 `DocumentService` 接口而不是 `DocumentMapper`。
这样做有三个好处：一是依赖方向单一，便于画出模块依赖图；
二是可以在不破坏调用方的前提下替换实现；三是让模块边界在编译期就受到约束，
避免单体项目最常见的「哪里都能查哪里」的腐化。

全局异常与响应体也统一收口在 common 模块：所有 Controller 返回 `Result<T>`，
`BusinessException` 由 `GlobalExceptionHandler` 统一转成 `Result.error(400, msg)`，
其余未预期异常兜底为 500 且只对外暴露模糊提示，细节留在日志里。

## 二、文档入库链路

### 2.1 上传与解析

上传入口是 `POST /api/document/upload`，接收 multipart 文件与可选分类参数。
校验分三道：文件非空、大小不超过 50MB、扩展名在白名单内（`pdf` / `docx` / `md` / `txt`）。
三道校验都在 `DocumentServiceImpl.validateFile` 里完成，失败抛 `BusinessException`，
由全局异常处理器转成 HTTP 400。

校验通过后写 MinIO 对象存储（对象名按日期分目录，避免同名覆盖），
再向 MySQL 写入文档元数据并获取自增 ID，随后按文件类型分派解析器提取全文：
PDF 用 Apache PDFBox、Word 用 Apache POI、Markdown 与纯文本按 UTF-8 直接读取。

**上传阶段不自动向量化**，这是有意设计的：向量化要调用外部 Embedding API 且耗时较长，
放在上传请求里会让接口响应时间不可控；改为前端显式调用 `POST /api/document/embed/{id}`，
状态位 `embedding_status` 从 0（待入库）变为 1（已入库），也便于失败重试与幂等控制。

### 2.2 滑动窗口分块

分块参数为**窗口 512 个字符、重叠 64 个字符**，因此滑动步长是 512 − 64 = **448 个字符**。
实现见 `DocumentChunkService.splitText`：

- 文本长度 ≤ 512 时整块返回，不做无意义切分；
- 否则从 0 开始，每轮取 `[start, min(start+512, len))` 作为一个分块，然后 `start += 448`；
- 尾块抑制：当剩余长度小于一个步长时收尾，且**只有当剩余长度大于重叠量 64 时才单独成块**，
  否则丢弃——因为剩余不足 64 字符与上一块几乎完全重复，保留只会产生近重复的碎片块，
  既浪费向量存储又会造成检索结果重复。

用具体数字验证算法行为：长度 1000 的文本切出 3 块（512 / 512 / 104）；
长度 960 的文本切出 2 块（512 / 512），剩余 64 字符因等于重叠量被抑制。
这两个边界值已写入验收测试 A2-06 固化。

为什么要重叠？因为语义可能正好落在切块边界上被切断——比如「向量维度是 2048」这句话
被切成「向量维度是 20」和「48」，两块的语义都不完整，检索时都可能匹配不上。
重叠 64 字符保证边界处的关键信息至少能在一块中完整出现。
反过来，如果把重叠设成 0，边界信息丢失会直接拉低命中率；
重叠设得过大则会产生大量冗余分块，推高存储成本与检索噪声。

### 2.3 Embedding 向量化

向量化由 `EmbeddingService` 调用智谱 AI 的 embeddings 接口完成，
模型为 **embedding-3，输出 2048 维**稠密向量——这个维度必须与 Milvus collection schema
中 `embedding` 字段的维度严格一致，否则插入时直接报错。

接口设计上做了两件事：一是**客户端分批**，把请求按 64 条一批切片（对齐服务商单请求上限），
避免一次提交几百个分块被拒；二是**结果缓存**，`embedSingle` 用 `ConcurrentHashMap.computeIfAbsent`
按文本缓存向量，key 前缀带模型版本号，这样切模型或改维度时旧缓存自动失效。
缓存上限目前是类内硬编码常量 5000，注意：`application.yml` 里的
`rag.retrieval.embed-cache-limit` 虽然能绑定到配置类，但 `EmbeddingService` 并未注入配置类，
所以改 yml 不会生效。

Embedding 的本质是把文本映射到高维空间的点，语义相近的文本在空间中距离更近
（「苹果手机」与「iPhone」接近，而与水果「苹果」较远）。这就是向量检索能跨越字面差异召回的原因，
也是 RAG 必须做向量化的原因——关键词匹配做不到这种语义泛化。

## 三、检索链路

### 3.1 Milvus collection 结构

主检索 collection 名为 `rag_document_chunks`，字段如下：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Int64（主键，autoID=false） | 直接复用 MySQL `document_chunk.id`，两库主键对齐便于回查 |
| content | VarChar(4096)，enable_analyzer=true | 分块原文，开启分析器供 BM25 分词 |
| document_id | Int64 | 所属文档，用于检索层用户隔离的 expr 过滤 |
| embedding | FloatVector(2048) | 稠密语义向量 |
| bm25_vector | SparseFloatVector | 稀疏向量，由服务端 Function 自动生成 |

collection 上注册了一个 BM25 Function：名 `text_bm25_emb`，
输入字段 `content`、输出字段 `bm25_vector`。插入数据时服务端会**自动**对 content 分词并生成稀疏向量，
因此应用层只需写 content 与 embedding，不需要自己算 BM25 权重。

索引方面，`embedding` 使用 AUTOINDEX + COSINE 度量，`bm25_vector` 使用 AUTOINDEX + BM25 度量。
**两个索引缺一不可**：只建稀疏索引时执行 `loadCollection` 会报
`there is no vector index on field: [embedding]`，collection 无法加载，检索直接不可用。

长期记忆使用独立的 `qa_memory` collection，与文档向量物理隔离，
避免历史问答内容混进文档检索结果。

### 3.2 相似度度量：COSINE 与欧氏距离

本项目统一使用**余弦相似度（COSINE）**。余弦相似度衡量两个向量方向的夹角，
取值范围 [−1, 1]，只关心方向不关心长度；欧氏距离衡量空间中两点的直线距离，对向量长度敏感。

文本向量场景优先选余弦相似度，因为文本长度差异会放大向量模长，
而语义相似度本质上取决于方向而非绝对距离。举个例子：同一句话重复两遍与说一遍，
方向几乎相同（余弦接近 1），但欧氏距离明显变大——用欧氏距离就会误判为不相似。

工程上的关键细节是**阈值要按度量校准**：COSINE 下中文短句的相似度普遍偏低，
0.3～0.5 就已经算不错的相关性，所以项目把 `minScore` 定为 0.35；
如果换成欧氏距离，阈值语义完全不同，不能沿用同一个数。
另外 v1 SDK 检索时通过 `nprobe` 参数控制 IVF 类索引的探测桶数，
调大能提升召回率但增加延迟，本项目取 10。
需要强调的是：当前混合 collection 用的是 AUTOINDEX（Milvus 内部自适应选择），
`ensureCollection` 里那套 IVF_FLAT + nlist=1024 是 v1 稠密 collection 的建表逻辑，
两者属于不同路径，不要混为一谈。

### 3.3 BM25 混合检索与 alpha 融合

单一稠密向量检索的短板是**词面精确匹配弱**：查询里出现一个罕见专有名词（比如错误码、函数名），
稠密向量可能因为语义泛化而召回不到，而词面匹配恰恰能一击命中。稀疏检索（BM25）补的就是这一块。

本项目的混合检索在应用层做分数融合，实现见
`MilvusService.hybridSearch(queryText, queryVector, topK, documentIds)`：

1. 稠密路：走 v1 SDK 的 `search`，按 `document_id in [...]` 过滤后取 TopK；
2. 稀疏路：走 v2 SDK，把查询原文包成 `EmbeddedText` 交给服务端自动 BM25 分词，
   检索字段 `bm25_vector`，filter 用同样的 document_id 表达式；
3. **加权融合**：`score = alpha × 稠密分 + (1 − alpha) × 稀疏分`，alpha 默认 **0.7**（偏重语义路），
   按 chunkId 用 `Map.merge` 累加两路分数后降序取 TopK。

这里有个必须记住的边界：**两路分数量纲不同**，COSINE 是 [−1,1]，BM25 是无上界的对数分数，
直接加权相加只是工程近似。更严谨的做法是 RRF（Reciprocal Rank Fusion），
即 `score = Σ 1/(k + rank_i)`，只依赖排名不依赖分值，天然免去量纲问题。
另外 Milvus 2.5 服务端也内置了 HybridSearch + Ranker，本项目选择应用层融合是为了更可控、便于调试。

降级行为：如果 collection 未按 BM25 结构建立（缺 `bm25_vector` 字段或 Function），
稀疏路会抛异常，此时 catch 住并**自动退化为纯稠密检索**，保证问答主流程不中断——
这是「可用性优先于效果」的典型取舍。

### 3.4 Rerank 精排

召回与精排是两件事。召回（混合检索）负责「别漏」，所以放宽到 **recall-top-k = 20** 条；
精排（Rerank）负责「排准」，用交叉编码器把 query 与每个候选**联合编码**后打分，
精度明显高于双塔向量的一次性向量相似度，最终只保留 **rerank-top-n = 5** 条进入提示词。

为什么必须先召回再精排？因为交叉编码器的计算量与候选数成正比，
把全库几万个分块都过一遍交叉编码器是不可接受的；而向量检索快但粗。
「粗召回 + 精排」是工业界标准的两阶段范式：用便宜的模型缩小候选集，用贵的模型决定最终顺序。

实现上调用智谱的 rerank 接口，模型名 `rerank`，请求前把候选文本截断到 500 字符控制体积与计费。
**注意一个容易踩的坑**：Rerank 会用 `relevance_score` **覆盖**原来的向量相似度分数，
因此后续的 `minScore` 阈值过滤、以及前端展示的「相似度百分比」，
用的其实都是重排分数而不是向量相似度。这一点在文档中必须说清楚，否则容易被追问穿。

降级路径：Rerank API 失败或响应结构异常时，退回「按原向量分数排序取前 N」，
召回集不变，所以答案不会错、只是可能不是最优。

## 四、生成与会话

### 4.1 问答链路完整顺序

`ChatServiceImpl.ask` 的编排顺序是：

1. **先落库提问**：即使用户提问之后检索或 LLM 失败，提问记录也保留，便于排查与续聊；
2. 问题向量化；
3. 取当前用户已向量化文档 ID 列表（`embedding_status=1`），作为检索层隔离条件；
4. 旁路召回长期记忆（只取本用户，异常时返回空列表，不阻断主链路）；
5. 查询改写（LLM 低温度 0.2）→ 混合检索召回 20 条 → Rerank 精排 5 条；
6. 按 `minScore = 0.35` 过滤，**过滤后为空则直接返回兜底文案，不调用 LLM**；
7. 拼接带编号的 context（`【参考1】…`），若召回命中长期记忆则追加「历史问答记录」段；
8. 调 DeepSeek 生成回答；
9. 写 sources JSON（每条含 chunkId、score、content 预览），落库助手消息并返回。

第 6 步的兜底文案是「知识库中没有找到足够相关的内容，请换个问法或先上传相关文档。」——
这一步是**防幻觉的硬闸门**：把空上下文交给 LLM，模型几乎必然开始编造，
所以宁可直接拒答。

### 4.2 长期记忆与阈值门槛

长期记忆存的是问答对：写入时把「问题\n回答」向量化后存入 `qa_memory`（回答截断 200 字符防膨胀），
召回时按 **相似度 > 0.5 取 Top3**，格式化成 `Q:…\nA:…` 注入提示词。

写入侧有一道**质量门槛**：只有当本次检索的重排最高分 **≥ 0.6** 时才落库。
这个设计的理由是——长期记忆会跨会话复用于后续提问，一旦低质回答（比如兜底文案、
或者相关性很差的拼凑答案）被写进记忆，它会持续污染后续所有相关提问，且很难被发现和清理。
用检索分数做门槛，等价于要求「这条问答有可信的来源支撑」才允许进入长期记忆。

### 4.3 JWT 认证流程

登录时 `AuthController` 校验密码后签发 JWT（HS256 签名，有效期 24 小时 = 86400000 毫秒），
payload 里放 userId。客户端把 token 存在 localStorage，
之后每次请求由 axios 请求拦截器注入 `Authorization: Bearer <token>` 头。

服务端由 `JwtInterceptor` 拦截 `/api/**`：取出 Authorization 头、截掉 `Bearer ` 前缀、
校验签名与过期时间、解析出 userId 后写入 `UserContext`（ThreadLocal）供全链路取用。
白名单只精确排除登录、注册与 Knife4j 文档相关路径——
**不能图省事写成 `/api/auth/**`**，否则 `/api/auth/me` 会被一并放行，
导致拿不到 userId 而恒定报未登录。

为什么用 JWT 而不是 Session？因为要无状态、可水平扩展：服务端不存会话，
校验只需本地验签，不需要 Redis 或粘性会话。

## 五、Agentic 能力

### 5.1 Function Calling 与 ReAct 的关系

这两者常被混为一谈，实际上**Function Calling 是能力，ReAct 是编排循环**。

Function Calling 是模型侧的能力：请求里带上 `tools`（每个工具含 name、description 与参数的
JSON Schema），模型可以在回答里返回结构化的 `tool_calls`，指明要调哪个工具、参数是什么。
它相比「让模型输出 JSON」的优势是：约束由 schema 保证、解析不靠正则或提示词哄、错误率低。

ReAct 是应用侧的循环：思考（模型决策）→ 行动（执行工具）→ 观察（把结果回填成 tool 消息）
→ 再思考，直到模型给出最终答案。本项目 `AgentExecutor` 用
`rag.agent.max-iterations = 5` 作为循环上限，防止模型反复调用同一工具形成死循环；
超限时返回「这个问题步骤较多，请拆分成几个小问题再问。」而不是报错。

实现上有一个 deepseek 特有的坑：思考模式（如 deepseek-v4-flash 的 thinking）
返回的 assistant 消息必须**原样回填**，包括 `reasoning_content` 与 `tool_calls` 字段。
如果用 POJO 转 Map 会导致字段名退化成 Java 风格（`reasoningContent`），
API 会拒绝并报「reasoning_content must be passed back」。
所以代码里用 Jackson 的 `readTree` 保留原始 JSON 字段名，并补上 `type: "message"`。

工具注册用注册表模式：`ToolRegistry` 构造器注入 `List<Tool>`，
Spring 自动收集所有实现（`query_document_stats`、`query_document_list`、`generate_report`），
新增工具只需加一个 `@Component` 实现类，注册表零改动——这是开闭原则的直接体现。

### 5.2 意图路由与多 Agent 编排

`OrchestratorAgent` 先做意图路由（`RouterServiceImpl`，temperature 0.1 求稳定），
把问题分到三条链路：STATS（查文档统计/列表，走工具）、DOCUMENT（问文档里的知识点，走 RAG）、
HYBRID（两者都要，组合回答）。解析容错策略是「非法输出一律回落到 DOCUMENT」——
宁可多检索也不漏答，保证主流程永远有结果。

分派后进专用子 Agent 执行，最后交给 `CriticService` 做反思评审（LLM-as-Judge）：
若判定不合格，则带着评审意见重写一次，重写次数上限
`rag.agent.critic-max-retry = 1`，硬控成本与延迟，防止自我修正无限循环。

### 5.3 熔断器

`LlmCircuitBreaker` 用 `AtomicInteger` 做连续失败计数、
用 `volatile long openUntil` 记录熔断打开截止时间，构成一个简化的两态状态机（关闭 / 打开）：

- 调用前 `tryAcquire()`：若当前时间早于 `openUntil` 则拒绝调用，直接走兜底文案；
- 调用失败 `onFailure()`：计数 +1，达到阈值 **5 次**时打开熔断，持续 **60000 毫秒（60 秒）**，
  同时把计数清零；窗口结束自动恢复放行；
- 调用成功 `onSuccess()`：计数清零。

**边界必须说清**：这个熔断器目前只被 `AgentExecutor` 使用，
也就是**只覆盖 `/api/agent/ask` 这条 Agent 链路**。
主问答链路 `/api/chat/ask` 没有接熔断器，它的可用性靠各自的降级路径保证
（改写失败用原句、检索与记忆异常静默、Rerank 失败退回原分、空召回走兜底文案）。
把项目描述成「全链路熔断」是不准确的。

熔断与限流的区别值得单独记一句：**限流保护自己**（控制入口流量不超过自身处理能力），
**熔断保护下游**（下游持续失败时主动切断调用，给它喘息时间，同时避免自己的线程被拖死）。
